Understanding the code, step by step

Once the robot responds, it is worth looking at what happens inside it. You do not have to read all seven files from beginning to end. Start with one simple question: what happens between pushing the joystick and the wheels moving?

The following excerpts come from the guide's ZIP. Their executable statements are unchanged; comments are translated into English for readability. They illustrate specific parts of the program. To upload it to the board, use the complete robot_firmware directory, not these excerpts alone.

A map of the seven files

robot_firmware.ino
Starts the subsystems, connects to Wi-Fi, and runs the main loop.
robot_config.h
Collects passwords, pin assignments, speed limits, and the other settings.
robot_motors.h
Turns joystick positions into movement for the left and right sides, with gradual changes and a check for missing commands.
robot_camera.h
Configures the camera and the memory used for its frames.
robot_web.h
Serves the page, commands, and video stream. Light control is here too.
robot_web_ui.h
Contains the HTML page and JavaScript that run in the phone's browser.
robot_audio.h
Sends playback and volume commands to the DFPlayer Pro.

A useful first distinction: C++ runs on the ESP32-CAM. The JavaScript in robot_web_ui.h runs on the phone. The two sides communicate over Wi-Fi.

What happens when the robot powers on

setup() runs once at startup. First it holds the motor pins LOW and turns off the flash. Then it prepares motor control, light, camera, and audio. Finally it starts Wi-Fi, the web servers, and, if suitable memory partitioning is available, Wi-Fi upgrading.

loop() repeats continuously:

{% capture firmware_excerpt_1 %} ```cpp void loop() { motors::update(); // ramp + 500 ms failsafe light::update(); audio::update(); // sends queued AT commands #if ENABLE_OTA if (s_otaReady) ArduinoOTA.handle(); #endif delay(2); } ``` {: file="robot_firmware.ino" } {% endcapture %} {{ firmware_excerpt_1 | markdownify }}

Each pass lets the motors move closer to their target speed, applies any light change, and sends the next audio command. ArduinoOTA.handle() services wireless upgrades when OTA is ready. delay(2) is a short pause, not an instruction to drive the robot for two seconds.

The HTTP handlers run on the servers started by web::begin(). That is why you will not find a web::update() call inside loop().

From a finger movement to a command

On the phone, the joystick position becomes two numbers: x for left/right and y for reverse/forward, ranging from −100 to 100. While you hold it, the page sends that position roughly every 50 ms, or 20 times per second.

For example, J,20,60 means “a little right and well forward”. The message reaches /ws, the WebSocket connection: a channel kept open for exchanging small messages. In robot_web.h, the command is recognised here:

{% capture firmware_excerpt_2 %} ```cpp case 'J': if (readInt(p, -1000, 1000, &a) && *p++ == ',' && readInt(p, -1000, 1000, &b)) { motors::setJoystick(a, b); return true; } break; ``` {: file="robot_web.h" } {% endcapture %} {{ firmware_excerpt_2 | markdownify }}

The page retries when the connection is lost. After three WebSocket failures, it enables fallback HTTP requests: /control for the joystick and /cmd for other commands. Both approaches reach the same firmware control functions.

When you release the joystick, the phone sends J,0,0 three times, 60 ms apart. If the tab moves into the background, it also tries to send a stop command.

How it turns without a steering wheel

The robot has two drive groups: the two left motors and the two right motors. Turning changes the relationship between their speeds. The main calculation in motors::setJoystick() is:

{% capture firmware_excerpt_3 %} ```cpp int l = y + x; int r = y - x; // normalise to |l|,|r| ≤ 100 while preserving their ratio int m = max(abs(l), abs(r)); if (m > 100) { l = l * 100 / m; r = r * 100 / m; } ``` {: file="robot_motors.h" } {% endcapture %} {{ firmware_excerpt_3 | markdownify }}

With x = 0, both sides receive the same value and the robot moves straight. With x = 20 and y = 60, the results are 80 on the left and 40 on the right: the left side requests more speed, turning the robot right. If the absolute magnitude of either value exceeds 100, normalisation scales both down while preserving their ratio.

Before this calculation, the program clamps inputs to −100…100 and ignores deviations smaller than 8% on either axis. Afterwards, it applies INVERT_LEFT and INVERT_RIGHT if either side needs reversing.

The result does not go straight to the motor as a percentage. pctToDuty() converts it into a PWM value. PWM switches the output on and off rapidly; the duty specifies how much of each cycle stays on. The supplied ZIP uses these settings:

{% capture firmware_excerpt_4 %} ```cpp #define MAX_DUTY 166 // ≈ 65 % #define MIN_DUTY 77 // approximately 30%; below this the motors do not start #define JOY_DEADZONE 8 // % - joystick dead zone #define RAMP_UP_STEP 6 // maximum duty increase per step (acceleration) #define RAMP_DOWN_STEP 20 // maximum duty decrease per step (braking) #define RAMP_PERIOD_MS 10 // ramp interval #define FAILSAFE_MS 500 // stop if no command arrives for this duration ``` {: file="robot_config.h" } {% endcapture %} {{ firmware_excerpt_4 | markdownify }}

At 8-bit resolution, the scale is 0…255. A value of 166 is about 65%, and 77 is about 30%. A zero command remains zero; a nonzero command maps into the range between those limits. Starting from rest, the ramp begins at minimum duty and then approaches the target, rather than immediately requesting the maximum value.

To understand this setting, remember that PWM is not a voltage regulator. The limit is a parameter of this firmware, not a measurement of actual motor voltage or current.

What happens when drive commands stop arriving

Every accepted joystick command updates the s_lastCmdMs timestamp. If more than 500 ms pass without a new command, motors::update() does this:

{% capture firmware_excerpt_5 %} ```cpp if ((int32_t)(millis() - s_lastCmdMs) > (int32_t)FAILSAFE_MS) { s_targetL = 0; s_targetR = 0; } ``` {: file="robot_motors.h" } {% endcapture %} {{ firmware_excerpt_5 | markdownify }}

It sets the targets to zero, then the ramp brings the outputs toward zero. The 500 ms value is therefore the threshold for detecting missing commands, not a promise that the wheels physically stop at precisely that instant.

The P message is separate: it asks for the robot's status and lets the page indicate connectivity. It does not refresh the time of the last driving command. A connection that still answers pings is therefore not enough on its own to keep the motors moving.

Why the camera uses its own port

The control page opens on port 80. Video arrives separately on port 81 at /stream. MJPEG is a sequence of JPEG images that the browser displays as a live stream. A separate server keeps continuous image transmission away from the command handler.

In robot_camera.h, the availability of PSRAM—the board's additional memory—determines the frame settings:

{% capture firmware_excerpt_6 %} ```cpp if (psramFound()) { c.frame_size = CAM_FRAME_SIZE; c.jpeg_quality = CAM_JPEG_QUALITY; c.fb_count = 2; c.fb_location = CAMERA_FB_IN_PSRAM; } else { Serial.println("[ΚΑΜΕΡΑ] Δεν βρέθηκε PSRAM – έλεγξε ότι η πλακέτα είναι \"AI Thinker ESP32-CAM\""); c.frame_size = FRAMESIZE_QVGA; c.jpeg_quality = 15; c.fb_count = 1; c.fb_location = CAMERA_FB_IN_DRAM; c.grab_mode = CAMERA_GRAB_WHEN_EMPTY; } ``` {: file="robot_camera.h" } {% endcapture %} {{ firmware_excerpt_6 | markdownify }}

With the defaults in robot_config.h, this means VGA 640×480, JPEG quality 12, and two buffers in PSRAM. Without PSRAM, the program uses QVGA, one buffer in internal DRAM, and a different capture mode. If camera initialisation fails, startup continues with a corresponding Serial message.

The page also monitors the frame counter f in the status response. If it remains unchanged for about three seconds while the picture was visible, it tries reconnecting the stream. This is separate from the motor-command failsafe.

Light and sound without holding up the joystick

The light is the built-in white LED on GPIO4. Commands L,1/L,0 turn it on or off, while B,n changes brightness on a 0…255 scale. The web handler stores the requested state and light::update() applies it.

For audio, ESP32 GPIO2 sends serial commands to the DFPlayer Pro's RX at 115200 baud. The DFPlayer's TX is not connected, so the firmware receives no acknowledgement from the module. The volume shown by the page is the requested value remembered by the program, not a measurement or reply from the DFPlayer.

Playing a track goes through playTrack():

{% capture firmware_excerpt_7 %} ```cpp inline void playTrack(int n) { if (n < 1) return; s_lastTrack = n; #if TRACK_BY_FILENAME enqueue("AT+PLAYFILE=/%02d.mp3", n); #else enqueue("AT+PLAYNUM=%d", n); #endif } ``` {: file="robot_audio.h" } {% endcapture %} {{ firmware_excerpt_7 | markdownify }}

With TRACK_BY_FILENAME = 0, the command selects a track by copying order. With a value of 1, it requests a specific filename such as /01.mp3. Commands enter a 16-slot queue and are sent by audio::update() after an initial 1.5 s wait, with at least 40 ms between them. For volume, only the latest pending value is retained, preventing a moving slider from filling the queue with intermediate levels.

Distinguishing the code from the diagram matters here

The ZIP sends AT+AMP=ON, and its comments describe a speaker directly on the DFPlayer Pro's L+/L−. The guide's diagrams and table describe an external DFR0119, with DACL → LIN and the speaker connected to that external amplifier. These are different descriptions of an audio arrangement. The code explanation does not change the diagram's wiring; read the collected clarification before choosing which arrangement to follow.

Wi-Fi and upgrading without the MB base

If STA_SSID is empty, the robot creates its own network, Robot-4WD: Access Point, or AP mode. If you supply home-network credentials, it tries connecting as a station, or STA. In this ZIP, STA_TIMEOUT_MS is 20000, or 20 s. If it cannot connect within that interval, it prints diagnostics, scans available networks, and returns to AP mode.

OTA means Over The Air: you send the next version over Wi-Fi. Suitable memory partitioning is needed from the first USB upload. The code checks for a next update partition before enabling the service.

When an upgrade starts, it runs the following handler:

{% capture firmware_excerpt_8 %} ```cpp motors::lockOut(); // set motors to 0 and ignore joystick commands light::set(false); light::update(); web::stopStream(); // release Wi-Fi/CPU resources used by the camera stream ``` {: file="robot_firmware.ino" } {% endcapture %} {{ firmware_excerpt_8 | markdownify }}

lockOut() immediately sets the outputs to zero and ignores new joystick commands. The light turns off and the camera stream ends. This handler is separate from the ordinary failsafe, because the update process may keep loop() busy. If OTA fails, the error handler restarts the ESP32.

Where to look when you want to change something

For common adjustments, start with robot_config.h. You do not have to modify the server or drive algorithm just to change a password or correct a reversed side.

  • Network and passwords: AP_SSID, AP_PASSWORD, optionally STA_SSID/STA_PASSWORD, and the separate OTA_PASSWORD.
  • A whole side runs backwards: INVERT_LEFT or INVERT_RIGHT. If only one motor on the same side is reversed, check its wiring first.
  • Image orientation and size: CAM_VFLIP, CAM_HMIRROR, CAM_FRAME_SIZE. Keep the pin mapping for this AI-Thinker board.
  • Audio: DFP_DEFAULT_VOLUME, TRACK_COUNT, TRACK_BY_FILENAME. Default volume is 20 and there are eight track buttons.

Change one thing at a time. Upload the version, read the Serial messages, and repeat the relevant test with the wheels off the ground. That way, you know which change produced which result.
